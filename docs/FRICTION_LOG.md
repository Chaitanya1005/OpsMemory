# Meko Friction Log

Running log of real limitations hit while building OpsMemory. Source for the final Meko feature proposal.
"Verified" entries were reproduced against the live service by `npm run spike:meko`.

| # | Date | Area | Friction | Current workaround | Affected |
|---|------|------|----------|--------------------|----------|
| 1 | 2026-10-31 | Memory scoping | Verified: `agent_id` doesn't filter `memory_search` / `memory_get_all`. The tool description says search "is cross-agent". Two agents in one datapack can't keep memories private from each other. | One datapack per agent context; isolation is per datapack. | Multi-agent apps run under one service account |
| 2 | 2026-10-31 | Promotion semantics | Undocumented until tested: promotion *moves* a memory out of private memory and into the knowledge base. Afterwards `memory_search` no longer returns it; `knowledgebase_search` does, tagged `metadata_filters.source = "memory"`. | Rely on this: "verified" = promoted = served from the KB. Unverified findings stay in private memory. | Anyone building a verified tier |
| 3 | 2026-10-31 | Response schemas | MCP reference gives no response shapes. Live input schemas are richer than the docs, e.g. `context_search` has undocumented `prompt` and `verify` params. | Spike captures real responses; zod schemas written from them. | Every programmatic integrator |
| 5 | 2026-10-31 | Forgetting | Promotion can't be reversed via MCP; collective memory can only be deleted in the portal. | Correct/forget offered before promotion; after promotion the UI links to the portal. | Users who promote a wrong resolution |
| 6 | 2026-10-31 | Verification metadata | No first-class approver/approval timestamp. `metadata` is not carried into the KB chunk after promotion; the KB chunk only has `source`, `agent_id`, `memory_id`. | Put approval facts (approver role, timestamp, incident id) in the memory *text* so they survive promotion. | Teams needing auditable knowledge |
| 8 | 2026-11-01 | Quotas | Free tier lifetime caps: 1,000 each for `memory_search`, `knowledgebase_search`, `context_search`, `conversation_add_message`. | Budget calls per investigation; one spike run uses ~6 quota-counted calls. | Demos, CI tests, eval loops |
| 9 | 2026-11-01 | Transport | Intermittent `ECONNRESET` / `fetch failed` on fresh MCP connections (seen 3 times). | Bounded retry on connect and on transport errors. | Every integrator |
| 10 | 2026-11-01 | Docs vs API | Verified: documented REST `POST /datapacks/{id}/knowledge-bases/upload` returns 404, while `GET …/knowledge-bases/documents` returns 200. | Use MCP `knowledgebase_upload_document` (presigned S3 POST) + `knowledgebase_document_status`. | App builders adding runbooks |
| 11 | 2026-11-01 | Bug | Verified: `memory_update` on a promoted memory fails with `Error calling tool 'memory_update': Object of type UUID is not JSON serializable`, not the documented `memory_is_promoted`. | Treat any error as "promoted content is read-only". | Correction UIs |
| 12 | 2026-11-01 | Recall gap | Verified twice: `context_search`'s `knowledge_base` bucket was empty for a query on which `knowledgebase_search` returned the promoted resolution (rerank 0.9999). | Knowledge Agent calls `knowledgebase_search` directly for verified knowledge. | Anyone relying on `context_search` as the single recall call |
| 14 | 2026-11-01 | Forgetting verified knowledge | Verified: a promoted memory's KB chunk has `document_id` = its conversation id, but `knowledgebase_delete_document` on that id returns `NOT_FOUND`. There is no MCP path to retract a wrong verified resolution. | Portal-only; the e2e test runs in separate `opsmemory-e2e-*` datapacks so test promotions never reach the demo datapacks. | Teams that promote a wrong fix; anyone testing promotion |
| 15 | 2026-11-01 | Latency | Verified across 3 runs: `memory_search` takes ~10.5s even on an empty datapack; `knowledgebase_search`, `memory_add` and `memory_promote` take ~1s. | Accept for now (one call per investigation); parallelise with KB search if needed. | Interactive apps doing recall on the request path |
| 16 | 2026-11-01 | Rerank signal | `rerank_score` was ≥0.98 for every KB hit, including a resolution for a different incident, so it can't serve as a relevance threshold. | Knowledge Agent asks the LLM to judge applicability of each retrieved item and may only cite returned refs. | Anyone filtering recall by score |
| 13 | 2026-11-01 | Privacy | `memory_get_all(promoted=true)` returns `promoted_by_name` and `promoted_by_email` for every row. | Strip these fields before anything reaches the UI or the LLM. | Apps exposing knowledge to viewers |
| 17 | 2026-11-01 | Idempotency | Write tools (`memory_add`, `memory_promote`, `conversation_create`, `conversation_add_message`) take no idempotency key. After a transport error the client can't know whether the write was applied, so retrying risks duplicates. | Client never retries these ops (`uncertain_outcome`); approval persists each confirmed step and reconciles before writing again. | Any app retrying writes |
| 18 | 2026-11-01 | Reconciliation | Verified: `memory_get_all` returns one page (`page_size` 20) plus `total`, with no pagination arguments; personal rows have no `metadata`, only `conversation_id`; promoted rows are only in the `promoted=true` listing, under a different key (`promoted_memories`). | Match approval memories by their unique approval `conversation_id`; if a listing exceeds one page, stay `needs_reconciliation`. | Apps reconciling uncertain writes |

## Resolved

- **#4 Promotion timing:** `memory_add` returns `results[].id` synchronously, and `memory_promote` on that id immediately succeeded (`inserted_ids`) in both runs.
- **#7** merged into #5 and #11.
